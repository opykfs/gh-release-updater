# PRD：GitHub 更新检测器（Android 个人工具）

## 0. 需求理解摘要

用户需要一款**仅自用、不上架**的安卓工具：读取手机已安装应用的版本号，将「已安装应用」手动绑定到「GitHub 仓库」，打开应用即自动调用 GitHub Releases API 比对版本；发现新版本后询问是否下载，下载完成后由用户手动点击确认，再拉起系统安装器完成安装；全程遵循 Material Design 3 设计规范。

## 1. 项目信息

- **语言**：简体中文
- **目标平台**：Android（用户自有设备，个人使用，不上架）
- **建议技术栈**：Kotlin + Jetpack Compose + Material 3（技术侧预判，供参考）
- **项目名称**：github_updater（snake_case）
- **文档版本**：v1.0

## 2. 产品定义

### 2.1 产品目标（一句话）

让用户在自己手机上，用最少的手动步骤，追踪「从 GitHub 发布的应用」是否有新版本，并在本人确认后完成下载与安装。

**补充描述**：应用不面向大众市场，核心价值是省去「反复打开 GitHub Releases 页面人工核对版本号」的繁琐过程；下载与安装必须经过用户显式确认，保证可控与安全。

### 2.2 目标用户与使用场景

**角色**：个人安卓用户（同时也是开发者/开源软件爱好者），惯于安装 GitHub 上发布的开源 APK。

用户故事：

1. 作为**安卓发烧友**，我想把手机里已安装的某个开源应用和它的 GitHub 仓库绑定起来，这样我能在一个地方统一追踪所有这类应用的更新。
2. 作为**个人用户**，我想打开应用后自动检查各追踪项的版本是否有更新，这样不必每次手动访问 GitHub Releases 页面比对版本号。
3. 作为**谨慎的用户**，我想在检测到更新时先看到提示、确认后再下载，下载完成后再次确认才安装，这样我能掌控每一步，避免被自动静默升级。
4. 作为**软件维护者本人**，当 GitHub 仓库或本机应用被删除时，我想能方便地删除/解绑该追踪项，保持列表整洁可用。

## 3. 需求池（技术规范 Requirements Pool）

| 优先级 | 需求编号 | 需求描述 | 对应原始需求 |
|--------|----------|----------|--------------|
| P0 | R1 | 读取本机已安装应用列表及版本号（包名、应用名、versionName/versionCode），供用户选择 | 需求 1 |
| P0 | R2 | 支持用户从已安装应用列表中选择应用，并手动填写其对应的 GitHub 仓库地址，建立「应用 ↔ 仓库」绑定/追踪关系并持久化 | 需求 2 |
| P0 | R3 | 打开应用后自动对全部追踪项调用 GitHub Releases API（latest release tag_name），与本机已安装版本比对，判定是否有更新 | 需求 3 |
| P0 | R4 | 检测到有新版本时弹出「更新提示」对话框，询问用户是否下载（展示新版本号与变化概览），仅在用户确认后开始下载 | 需求 4 |
| P0 | R5 | 下载完成后展示「安装确认」对话框，由用户手动点击确认后才拉起系统安装器（PackageInstaller / ACTION_VIEW）执行安装 | 需求 5 |
| P0 | R6 | 全应用视觉与交互遵循 Material Design 3（Material You 动态取色，主题色/组件规范） | 需求 6 |
| P0 | R7 | 追踪项支持删除/解绑（长按或编辑界面删除），应对仓库失效或应用卸载场景 | 隐含需求（支撑需求 2 的闭环） |
| P1 | R8 | 检测/下载过程中展示可见进度（下载进度条、百分比；检测中 loading 状态），下载支持通知栏进度展示 | 隐含需求（下载时长较长，需反馈） |
| P1 | R9 | 网络异常/仓库不存在/无 release 时给出明确错误提示，单项失败不影响其他项检测 | 隐含需求（保证检测健壮性） |
| P2 | R10 | 支持手动下拉刷新或「立即检测」按钮（除自动检测外的触发方式） | 隐含需求（补充自动检测） |
| P2 | R11 | 支持「跳过本次版本」功能（标记某版本已忽略，避免每次打开都提醒同一个新版本） | 隐含需求（提升个人使用体验） |
| P2 | R12 | 记录最近一次检测时间 / 上一次检测到的新版本 | 隐含需求（状态可追溯） |

## 5. 待确认问题（Open Questions）

1. **安装方式偏好**：是否需要「下载完成后可选：直接安装 / 分享/另存 APK 文件」？（默认仅安装）
2. **release 版本判定**：是否只认 `latest release`（不含 pre-release / draft），若最新版本为 pre-release 是否忽略？默认：忽略非正式版本。
3. **版本比较规则**：以 versionCode 还是 versionName 比较为准？（建议以 Release tag_name 与本地 versionName 做语义化比较，若存在 pre-release 场景需明确规则）
4. **自动检测时机**：除打开应用自动检测外，是否需要后台定时检测并通知？（个人工具建议不做后台常驻，仅打开时检测；如需则归入 P2）
5. **下载安装来源校验**：是否需对 GitHub 下载的 APK 做签名校验/包名一致性核对后再允许安装（降低风险）？默认：安装前提示来源为 GitHub，不额外校验。

## 6. 验收标准

> 标记：A1–A6 分别对应原始需求 1–6。

1. **A1（需求1）**：在「添加追踪」界面能够列出本机已安装应用，并正确展示其应用名、包名与版本号（versionName）。
2. **A2（需求2）**：用户可选择一个已安装应用并填写 GitHub 仓库地址完成绑定；绑定关系在应用重启后仍然保留；支持删除已绑定的追踪项（R7）。
3. **A3（需求3）**：打开应用后，程序自动向已绑定仓库的 GitHub Releases API 请求最新版本号；当仓库最新版本高于本机版本时，列表对应项显示「有新版本」状态；断网或仓库地址错误时显示明确错误而非崩溃（R9）。
4. **A4（需求4）**：检测到新版本时弹出「更新提示」对话框（展示当前/最新版本号）；只有用户点击「下载更新」后才开始下载，未确认不发起下载；下载过程有可见进度反馈（R8）。
5. **A5（需求5）**：下载完成后弹出「安装确认」对话框；只有用户点击「安装」后才拉起系统安装器；用户选择「稍后」则不触发任何安装动作。
6. **A6（需求6）**：应用全部页面（主界面、添加追踪、两个对话框）使用 Material Design 3 组件与主题（含动态配色、圆角卡片、Filled/tonal 按钮等），可通过人工视觉检查验收。
